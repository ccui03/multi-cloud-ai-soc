# 项目总体方案书（Project Charter）

- 项目名称：Multi-Cloud AI SOC
- 文档版本：2.0
- 状态：规划基线（Plan Baseline；技术实现状态另行跟踪）
- 日期：2026-11-26

## 1. 项目定位

Multi-Cloud AI SOC 是一个面向多云、多厂商安全设备的 AI 安全运营平台。项目首期以 Web Application Firewall（WAF）安全日志为切入点，建立统一的数据接入、字段发现、事件标准化、威胁检测、跨源调查和 AI 辅助研判能力。

项目不是某一家云厂商 WAF 的日志查看器，也不把 AI Agent 当作核心数据处理引擎。长期目标是：新增安全数据源时主要扩展接入适配器和字段语义映射，检测、关联、调查、报告等上层能力尽可能复用。

## 2. 背景与问题

企业可能同时使用多个云平台和不同厂商的 WAF。各产品在日志存储、API、字段命名、动作语义、时间格式和查询能力上存在差异。安全人员需要在不同控制台之间切换，手工搜索、整理和关联证据，导致调查效率低、研判口径不一致、调查过程难以复现。

项目拟解决：
- 多厂商日志查询入口分散、操作方式不一致。
- 原始字段和安全动作语义不统一，跨厂商无法直接比较。
- 告警和日志之间缺少自动化上下文关联。
- 调查依赖人工逐条查看日志，难以快速形成时间线和证据链。
- AI 分析缺少结构化证据、边界控制和审计能力。

## 3. 项目目标

### 3.1 产品目标
1. 提供统一的多厂商 WAF 数据源管理与查询能力。
2. 建立可扩展的字段发现、字段注册、标准化和版本管理体系。
3. 将原始日志、检测事件、告警、调查案例和分析报告分层管理。
4. 提供可解释、可追溯的安全检测与跨源关联分析。
5. 使用 AI Agent 提升告警分诊、调查、证据整理和报告生成效率。
6. 为后续威胁情报、事件管理和经审批的自动化响应预留扩展能力。

### 3.2 技术目标
- 建立厂商无关的核心数据契约和可插拔 Provider Adapter。
- 将厂商 API、认证、分页、查询 DSL 和错误处理封装在接入层。
- 建立 Schema Discovery、Field Registry、Normalizer 和 Schema Evolution 流程。
- 建立统一安全事件模型，保留来源、原始字段引用、解析版本和证据链。
- 通过确定性规则、统计和查询筛选数据，再将有限上下文交给 LangGraph。
- 保证数据源凭据隔离、最小权限、日志脱敏、操作审计和人工审批。

## 4. 范围与分期

### 4.1 首期 PoC 范围
- 数据源：阿里云 WAF → SLS；腾讯云 WAF → CLS。
- 日志类型：首先覆盖 WAF 访问日志及可获得的安全检测/防护日志；不同日志类型的语义需分别建模。
- 能力：只读接入、批量 Schema 分析、字段映射、统一事件、基础检测/聚合、跨源调查、AI 分诊和报告。
- 部署：小规模、低成本、Docker Compose / 单机环境。
- 存储：原始日志默认留在厂商日志服务；项目侧仅保存必要事件、状态、证据引用、分析结果和审计元数据。

### 4.2 后续扩展范围
- 其他云厂商 WAF、第三方/本地部署 WAF。
- API 安全、Bot 管理、DDoS、IPS/IDS、Firewall、EDR 等安全数据源（按产品优先级逐步纳入，不承诺首期全部支持）。
- 威胁情报、攻击活动关联、事件生命周期管理。
- 经策略校验和人工批准的响应自动化。

### 4.3 明确不属于首期
- 替代成熟商业 SIEM 或 QRadar。
- 全量复制所有厂商原始日志，建设通用日志湖。
- 无审批的自动封禁、WAF 策略修改或其他云端写操作。
- 一开始部署 Kafka、OpenSearch、Redis、TheHive、Shuffle 或 Kubernetes。
- 面向公网的多租户 SaaS、生产级高可用和大规模分布式部署。

## 5. 核心设计原则

1. **Vendor-neutral core**：核心事件、检测和 Agent 工作流不依赖单一厂商字段。
2. **Adapter isolation**：厂商 API、SDK、认证和分页差异只存在于 Provider Adapter。
3. **Schema-driven**：通过字段注册表管理字段语义、类型、敏感级别、映射和版本，不靠散落在代码中的硬编码判断。
4. **Evidence first**：检测和 AI 结论必须可回溯到来源日志、查询条件和证据。
5. **Raw preservation**：标准化不能覆盖或丢弃原始证据；原始日志默认仍保存在源端。
6. **Deterministic before AI**：先过滤、聚合、规则检测和关联，再让 LLM 处理有限上下文。
7. **Secure by default**：最小权限、脱敏、提示注入防护、只读工具和审批门。
8. **Cost-aware**：查询范围、调用次数、返回量、存储、模型 Token 均需可度量和限额。

## 6. 用户角色

- 安全分析人员：查看告警、调查事件、审阅证据和报告。
- 平台管理员：管理数据源、凭据引用、字段注册表、查询策略和系统配置。
- 安全工程师：维护检测规则、关联规则和解析映射。
- 审计人员：检查查询、模型分析、审批和响应操作记录。

## 7. 成功指标与验收原则

PoC 至少评估以下指标，具体目标值在取得两家厂商真实样本和基准数据后确定：
- 数据源连接成功率、查询成功率、分页完整性和恢复能力。
- Schema 字段覆盖率、未知字段发现率、类型变化发现能力。
- 标准化关键字段映射准确率和未映射字段可追踪率。
- 去重准确性、事件时间准确性、迟到日志补采能力。
- 检测规则准确率、误报率和可解释性。
- AI 调查证据引用完整率、报告可复现性和人工节省时间。
- 每千条日志查询成本、单次调查耗时、数据库增长量和 LLM Token 成本。

## 8. 项目风险

| 风险 | 应对 |
|---|---|
| 厂商字段和动作语义不一致 | 官方文档 + 脱敏样本 + 字段注册表；未知语义保持 unknown |
| 厂商 API 能力差异 | 统一能力契约 + Adapter capability 声明，不强求所有厂商功能完全一致 |
| Schema 经常变化 | 自动画像、版本检测、兼容性测试和解析器版本管理 |
| 日志量和查询费用不可控 | 源端过滤/聚合、查询预算、时间窗口和结果上限 |
| AI 幻觉和提示注入 | 证据约束、结构化输出、日志作为不可信数据、人工复核 |
| 敏感数据外发 | 字段分级、脱敏、最小上下文、模型数据政策评估 |
| 错误响应影响业务 | 首期只读；后续策略校验、审批、TTL、回滚和审计 |

## 9. 当前已知状态与待确认事项

M0 的统一评审基线见 [M0 规划与设计基线](m0-baseline.md)。本节只记录已知项目状态，不将代码存在等同于能力验收。

### 9.1 当前技术状态（截至 2026-11-26）

- 项目代码骨架及部分 Provider Adapter / 接入模块已存在；已有测试通过记录，但具体能力仍以当前分支测试和真实环境验证结果为准。
- 阿里云 SLS 的近期真实查询联调返回 HTTP 403（GetLogs / LogRequestError）；当前不能认定阿里云数据源已通过端到端验收，需在 M1 核查 Region、Project/Logstore、RAM 权限和请求参数。
- 腾讯云 CLS 尚未进入本轮真实联调验证；不得将 Adapter 设计或代码存在表述为 CLS 已验收。
- PostgreSQL 持久化、Checkpoint、基础增量采集和 Schema Profiler 已有实现基础；统一事件语义、正式 Field Registry、检测/聚合质量和完整 LangGraph 工作流仍须按里程碑验收。
- 当前优先完成 M0 规划基线和 M1 数据源验证；不得因已有代码而跳过需求、数据语义和验收评审。

### 9.2 M0/M1 待验证事项

- 两家 WAF 实际可用的访问日志、安全检测/防护日志类型及其查询方式。
- 关键字段、WAF 检测/模块动作/最终动作/观察模式和 HTTP 状态的官方语义。
- SLS/CLS 的查询分页、时间边界、限流、返回量、延迟和实际计费。
- 增量查询间隔、窗口重叠和 1 天/7 天历史回溯切片的合理性。
- 数据量、查询预算、数据库保留期限和模型 Token 预算。

所有未验证项须在 M1 的 Capability Matrix、脱敏样本、查询记录和 Decision Log 中留证。
