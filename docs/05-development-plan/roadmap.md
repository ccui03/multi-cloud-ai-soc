# 项目总体计划与开发路线图（Project Plan & Roadmap）

- 版本：2.0
- 日期：2026-11-26
- 状态：规划基线；各阶段须通过 Exit Criteria 后才能进入下一阶段
- 计划原则：先定义产品和数据语义，再建设可复用平台能力；首期 WAF 聚焦，架构面向多厂商扩展。

## 1. 总体路线

项目分为八个阶段。阶段表示能力成熟度，不等同于固定日历周期；每阶段工期应在需求、资源和数据源条件明确后估算。

| 阶段 | 名称 | 目标 | 主要交付物 |
|---|---|---|---|
| Phase 0 | 产品与需求规划 | 明确用户、场景、范围、指标和厂商策略 | Charter、PRD、场景清单、优先级、验收标准 |
| Phase 1 | 数据源与能力验证 | 验证首批 WAF 数据源 API、日志类型、字段、成本和限制 | Vendor Capability Matrix、样本集、风险清单 |
| Phase 2 | 多厂商接入基础 | 建立通用 Adapter 契约、能力声明、配置和可靠查询 | Provider Framework、阿里云/腾讯云连接器 |
| Phase 3 | Schema 与标准化平台 | 自动画像、字段注册、版本管理和统一事件 | Schema Profiler、Field Registry、Normalizer、测试集 |
| Phase 4 | 检测与关联分析 | 从原始日志形成安全发现和跨源关联 | Detection Rules、Correlation Engine、Event Service |
| Phase 5 | AI 调查与报告 | 以证据驱动 Agent 完成分诊、调查和报告 | LangGraph Workflow、Tool Registry、Evaluation Set |
| Phase 6 | SOC 工作台与运营闭环 | 让分析人员管理告警、案例、证据和任务 | API/UI、Case Management、Audit、Observability |
| Phase 7 | 响应与企业化演进 | 在审批和策略控制下实现响应，评估生产部署 | Approval Gateway、Response Connectors、部署/容量方案 |

## 2. 各阶段详细计划与退出标准

### Phase 0 — 产品与需求规划（当前优先）

任务：
- 明确主要用户、日常工作流和最重要的 3–5 个使用场景。
- 明确首期产品边界：WAF 访问日志、安全事件日志、管理审计日志分别处理。
- 明确核心对象：数据源、原始记录、标准事件、发现/告警、调查案例、证据、报告。
- 确认首期仅阿里云 WAF/SLS 与腾讯云 WAF/CLS；其他厂商列入候选池，不提前承诺交付。
- 定义成功指标、PoC 预算、运行环境、数据保留和模型数据政策。
- 将已实现代码与计划需求分开标记，避免“代码已存在”被误认为“需求已验收”。

交付物：
- Project Charter、Requirements/PRD、核心用户场景和业务流程。
- 范围内/范围外清单、术语表、风险登记表。
- MVP 验收指标和测试策略。

Exit Criteria：
- 首期场景和范围经确认。
- 每项 P0 需求有可验证验收条件。
- 数据和模型安全边界明确。
- 无影响架构的重大未决问题。

### Phase 1 — 数据源与能力验证

任务：
- 分别确认阿里云 WAF 与腾讯云 WAF 的产品版本、日志类型、日志投递路径和权限。
- 验证查询 API、时间过滤、分页、排序、过滤、聚合、回查和限流。
- 采集受控脱敏样本，覆盖正常访问、规则命中、拦截、挑战、测试/观察模式、放行和异常场景（以实际可构造场景为准）。
- 统计字段覆盖率、字段共现、类型、枚举和样本时间分布。
- 记录查询成本、请求次数、延迟、数据量和日志延迟。
- 建立 Vendor Capability Matrix，明确每个厂商能力支持/不支持/未验证。

交付物：
- 每厂商日志类型清单、字段画像和语义证据。
- API/SDK 验证报告和脱敏回归样本。
- 查询成本与容量基线。
- Vendor Capability Matrix。

Exit Criteria：
- 两个首期数据源的只读连接和关键查询路径验证完成。
- 分页/时间窗口行为有可复现测试。
- 关键字段语义有文档或样本证据；未知语义明确标记。
- 查询预算和数据处理策略可执行。

### Phase 2 — 多厂商接入基础

任务：
- 定义 Provider Adapter 统一接口和 Provider Capability 声明。
- 统一数据源标识、凭据引用、连接健康、查询任务和错误模型。
- 实现认证、时间过滤、过滤表达式转换、分页、限速、退避、超时和错误映射。
- 实现独立 Checkpoint、历史回溯、断点恢复和幂等去重。
- 明确查询与采集分离：按需调查查询不应意外推进增量 Checkpoint。
- 为每个 Adapter 建立 mock contract tests 和脱敏集成测试。

交付物：
- Provider Framework 和 Capability Registry。
- 阿里云 SLS、腾讯云 CLS Adapter 验收记录。
- 可恢复查询/采集任务和运行指标。

Exit Criteria：
- 两个 Adapter 通过相同契约测试。
- 不支持的能力明确返回 capability limitation。
- 失败恢复、重复数据和迟到日志处理符合设计。
- API 凭据与数据源配置隔离且无敏感信息泄漏。

### Phase 3 — Schema 与标准化平台

任务：
- 建立厂商无关的 Schema Profiler，支持嵌套字段、类型、覆盖率、枚举、字段共现和 Schema Drift。
- 建立 Field Registry：按 provider/product/log_type/schema_version 管理字段定义。
- 对字段记录 documented、observed、inferred、unknown 等语义状态及证据来源。
- 定义字段敏感级别、脱敏规则和 LLM 可见性。
- 定义统一安全事件核心模型、Vendor Extension 和 Provenance。
- 实现可版本化 Normalizer、映射质量报告和回归测试。
- 动作语义必须拆分检测命中、模块动作、最终动作、测试模式和实际效果；未知值不推断。

交付物：
- Schema Profile、Field Registry 和变更审查流程。
- Normalized Security Event Schema。
- 两家首期厂商映射包和自动化测试集。

Exit Criteria：
- 关键字段映射可解释、可追踪、可回归。
- 新字段/类型变化能被发现，未经审查不自动改变语义。
- 原始证据和厂商扩展字段不丢失。
- 新增厂商不需要修改通用画像引擎和事件核心结构。

### Phase 4 — 检测与关联分析

任务：
- 建立规则检测框架：阈值、频率、Top-N、异常趋势、已知规则命中等。
- 区分日志、检测发现、告警和案例，不将每条访问日志都视为告警。
- 建立实体模型：IP、域名、URL/路径、规则、请求标识、账号/租户等。
- 建立时间窗口和实体关联策略，控制误关联。
- 对告警进行去重、聚合、优先级建议和证据打包。
- 通过历史样本构建基础检测评估集。

交付物：
- Detection Rule Framework。
- Correlation Engine。
- Event/Alert API 和可解释证据包。

Exit Criteria：
- 核心场景可从日志产生可追踪发现。
- 每个告警包含来源、时间、规则/逻辑、证据和置信度。
- 有基础误报评估结果。
- 不同厂商同义事件可以使用统一检测逻辑。

### Phase 5 — AI 调查与报告

任务：
- 定义 LangGraph 状态、节点、边界和失败恢复。
- 建立受控工具：事件检索、源端日志回查、统计聚合、情报查询（如获批准）。
- 工作流：告警分诊 → 调查计划 → 证据检索 → 时间线 → 假设验证 → 报告。
- 输出结构化结论、证据引用、置信度、不确定性和建议。
- 建立 Prompt Injection 防护、上下文裁剪、脱敏和 Token 预算。
- 建立评估集，比较无 Agent/规则分析与 Agent 辅助分析的效果。

交付物：
- LangGraph Investigation Workflow。
- Tool Registry 和 JSON Schema。
- 结构化调查报告。
- Agent Evaluation Dataset 与评估报告。

Exit Criteria：
- 结论可追溯到具体事件/查询证据。
- 不允许模型编造字段、规则、来源或工具结果。
- 日志中的不可信文本不能改变工具权限或系统指令。
- Agent 在成本、时延和准确性方面达到 PoC 设定目标。

### Phase 6 — SOC 工作台与运营闭环

任务：
- 提供数据源状态、采集状态、Schema 变化、事件/告警列表。
- 提供事件详情、调查时间线、证据、报告和人工反馈。
- 建立案例状态、负责人、备注、处理记录和审计。
- 提供查询、Agent 运行、错误、成本和系统健康监控。
- 完善用户认证、角色权限和数据访问隔离（按部署场景确定）。

交付物：
- FastAPI 稳定接口。
- 最小 React SOC 工作台。
- Case Management、Audit 和 Observability。

Exit Criteria：
- 分析人员能完成从告警到调查报告的基本流程。
- 查询和 Agent 运行均可审计。
- 系统运行状态、错误和成本可观察。

### Phase 7 — 响应与企业化演进

任务：
- 定义响应动作目录、风险等级、策略校验和审批流程。
- 每个响应连接器独立处理权限、幂等、TTL、回滚和执行结果核验。
- 默认 Dry-run；人工批准后才能执行写操作。
- 评估多租户、HA、备份恢复、密钥管理、升级和灾备。
- 根据实际规模评估 Kafka、OpenSearch/ClickHouse、Redis、Kubernetes 等组件，必须有容量数据支撑。

交付物：
- Response Gateway 与厂商响应连接器。
- 审批、执行、回滚和审计记录。
- 企业部署与容量规划。

Exit Criteria：
- 未经批准无法执行写操作。
- 响应有 TTL、回滚路径和结果验证。
- 部署、安全和容量测试通过。

## 3. 首期 MVP 建议边界

首期 MVP 不等于完整 SOC。建议只交付：
1. 两家 WAF 数据源只读接入。
2. Schema Discovery + Field Registry 的最小可用流程。
3. 统一 WAF Security Event。
4. 3–5 个有代表性的检测/调查场景。
5. LangGraph 告警分诊、证据收集和调查报告。
6. 最小 API/页面或可演示工作流。
7. 成本、审计和安全边界。

明确暂缓：通用 SOAR、复杂多租户、全量 SIEM 功能、全厂商覆盖、无审批自动响应。

## 4. 建议优先验证的业务场景

| 场景 ID | 场景 | 主要能力 | MVP 优先级 |
|---|---|---|---|
| UC-01 | 单条 WAF 安全事件研判 | 动作语义、规则、请求上下文、风险说明 | P0 |
| UC-02 | 同一来源 IP 高频攻击调查 | 时间窗口、IP 关联、Top-N、源端回查 | P0 |
| UC-03 | 多域名/多站点攻击关联 | Host、IP、路径和时间线关联 | P1 |
| UC-04 | 跨云相似攻击关联 | 多厂商事件标准化、实体/时间关联 | P1 |
| UC-05 | Bot/扫描/暴力尝试趋势分析 | 模块语义、频率和行为统计 | P1 |
| UC-06 | AI 自动生成调查报告 | 证据引用、假设、不确定性和建议 | P0 |
| UC-07 | 多阶段攻击活动关联 | 多类安全源、情报和案例图谱 | P2 |

## 5. 关键依赖关系

- Phase 0 决定场景和验收标准，是后续工作输入。
- Phase 1 提供真实数据、字段语义和 API 限制，是 Phase 2/3 的依据。
- Phase 2 提供可靠数据接入，是 Schema/检测的基础。
- Phase 3 的统一事件模型是 Phase 4/5 的共同输入。
- Phase 4 先提供确定性发现和证据，Phase 5 才有可靠的 Agent 调查对象。
- Phase 6 将能力产品化；Phase 7 依赖成熟的权限、审计和运营流程。

## 6. 计划管理规则

- 每个阶段先建立 Epic，再拆分可验收的 Issue。
- Issue 必须包含背景、范围、依赖、验收标准、测试方式和安全/成本影响。
- 未验证的 API/字段语义标记为 Unknown 或 Proposed，不写成事实。
- 每个厂商新增时复用统一模板：Vendor Profile、Capability Matrix、Sample Set、Field Registry、Adapter Contract Tests、Normalizer Tests。
- 阶段退出必须有验收记录；代码合并不等于阶段验收。
- 计划变更记录在 Decision Log / Change Log；重大架构变化使用 ADR。

## 7. 当前执行重点

当前优先完成 Phase 0 规划，不立即扩展代码：
1. 确认首期 3–5 个核心安全运营场景。
2. 确认 WAF 日志类型和模块边界。
3. 完成数据源能力矩阵和字段语义治理方案。
4. 定义 MVP 事件、告警、案例和报告对象。
5. 定义验收指标、测试数据集和成本预算。
6. 规划通过后再进入下一轮实现。

## 8. v2.1 业务方向与阶段计划补充

### 8.1 已确认决策
- 采用分层研判：告警先聚合，再关联形成攻击事件，必要时下钻单条日志。
- Security Incident 是主要 AI 研判对象；Alert Group 是降噪和事件候选层。
- 策略调整只提供建议，由安全人员人工执行；当前不开发自动封禁或 WAF 策略写入。

### 8.2 MVP 场景优先级
| ID | 场景 | 核心问题 | 优先级 |
|---|---|---|---|
| UC-01 | 告警聚合与降噪 | 如何把重复/相似告警变成可处理的告警组 | P0 |
| UC-02 | 攻击事件分层研判 | 告警代表真实攻击、疑似攻击、正常业务还是证据不足 | P0 |
| UC-03 | 正常业务误报识别 | 哪些命中更可能是正常请求，依据是什么 | P0 |
| UC-04 | 事件调查与证据下钻 | 如何用有限查询验证假设并形成时间线 | P0 |
| UC-05 | WAF 策略优化建议 | 哪些规则/路径/参数可能过于敏感，如何安全优化 | P0 |
| UC-06 | 跨域名/跨云攻击关联 | 不同站点和云平台的告警是否属于同一活动 | P1 |
| UC-07 | 规则质量与攻击趋势 | 哪些规则持续高误报、哪些攻击行为发生变化 | P1 |

### 8.3 阶段验收补充
**Phase 3 — Schema 与标准化**：区分访问日志、安全告警和策略/审计日志；分别建模检测结果、模块动作、最终动作、测试/观察模式和 HTTP 状态。关键事件可作为聚合、关联和证据输入。

**Phase 4 — 检测与关联**：建立 Alert Signal、Alert Group、Security Incident 三层对象；支持去重、窗口聚合、行为簇、多维关联、关联解释、错误合并拆分和人工纠正。Exit：代表性样本可形成可追溯告警组和事件候选，聚合前后数量可度量。

**Phase 5 — AI 调查**：Agent 默认接收 Evidence Pack；输出恶意、疑似恶意、疑似正常、已确认正常或证据不足，并给出支持证据、反证、置信度、严重性、缺口和策略建议。Exit：基准样本达到人工评审目标，成本和耗时可统计。

**Phase 6 — SOC 工作台**：提供事件队列、详情、时间线、证据、报告、策略建议和人工反馈；建议状态与执行状态分离。Exit：分析人员可完成查看、复核、确认、审阅建议和记录人工结果的闭环。

### 8.4 MVP 必须度量的指标
- 聚合降噪率与错误合并率。
- 事件关联准确性、错误合并/拆分比例。
- 各 verdict 分类的 Precision / Recall 和 Inconclusive 占比（基于人工标注评估集）。
- 证据引用有效率、反证覆盖率、无依据结论比例。
- 人工审核通过率、修订率、平均调查耗时。
- 策略建议接受率、拒绝原因、效果验证率。
- 每千条日志查询成本、每个事件模型成本和调查时延。

目标阈值应在取得脱敏真实样本和人工标注基准后确定，不预先编造数字。

## 9. Web 工作台开发规划补充（v2.2）

UI 不应全部推迟到最后一个阶段。为让日志查询和 AI 研判形成可验证闭环，采用基础工作台随核心能力同步建设、运营管理能力逐步完善的方式。

### Phase 2/3：基础 Web 与日志查询
- 建立登录、基础布局、导航、用户会话和 RBAC 接口。
- 实现 Log Explorer：数据源、时间范围、常用字段过滤、分页、详情和保存查询。
- 展示标准化字段、厂商扩展字段、字段语义状态和敏感字段脱敏。
- Exit：用户可在统一 UI 中对至少一个已验证数据源进行受控日志查询；权限和查询预算在后端生效。

### Phase 4：告警与事件工作台
- 实现 Dashboard 初版、Alert Center、Incident Center。
- 支持告警组成员查看、事件时间线、证据详情和从日志/告警到事件的双向导航。
- Exit：安全人员可在 UI 中从告警发现进入事件调查，查看聚合依据和证据。

### Phase 5：AI Copilot
- 实现 AI 对话页和事件上下文 Copilot。
- 支持自然语言查询、解释告警、事件调查、证据追问和研判报告。
- 展示查询范围、工具调用摘要、证据引用、结论置信度和数据缺口。
- Exit：AI 对话只能调用受控只读工具；用户可追溯回答所引用的日志/事件证据。

### Phase 6：SOC 管理运营
- 完善管理 Dashboard、策略建议审核、人工执行记录、报表和运营指标。
- 实现角色/数据范围管理、审计查询和成本视图。
- Exit：管理人员可掌握运营状态；安全人员能完成建议审核和反馈闭环。

### UI 交付顺序建议
1. 登录与应用框架、RBAC。
2. 日志查询与详情。
3. 告警/事件列表和详情。
4. AI 对话及上下文证据跳转。
5. 策略建议审核。
6. 管理 Dashboard、报表和系统管理。

前端页面围绕后端稳定的领域 API 逐步交付，不以一次性完成全部页面为前提。

## 10. UI 交互实施与验收顺序（v2.3）

### UI 交互设计决策
主模式为“独立页面 + 上下文联动”，全局 AI 助手采用右侧可展开面板。独立 AI 页面提供完整会话工作区，右侧面板适合在业务页面中快速提问和调查。

### 实施顺序
1. App Shell：左侧导航、中央内容区、全局 AI 入口和右侧 Drawer 框架。
2. Log Explorer 上下文：支持把选中记录、记录引用或过滤条件摘要明确传入 AI。
3. Alert/Incident 上下文：支持从告警组和事件详情打开 AI，并自动带入授权对象引用。
4. Agent Session 统一：右侧面板和独立 AI 页面复用同一个会话 ID、上下文快照和证据引用。
5. Evidence Navigation：AI 回答可跳回日志、告警组和事件详情。
6. Manager View：补齐管理总览、待审核建议、趋势和数据源健康视图。

### UI 交互 Exit Criteria
- 同一个 AI 会话可在右侧面板与独立页面之间无损切换。
- 页面上下文只有在用户明确操作时才加入或替换。
- 用户可辨认 AI 实际使用的是单条/多条记录、筛选摘要还是后端查询结果。
- AI 回答证据可定位，且不会因切换页面丢失会话。
- 所有查询仍经过统一权限、范围和成本校验。

## 11. MVP 收敛：先验证 AI 威胁分析价值（v2.4）

### 产品方向
第一版是简易的 AI WAF 日志威胁分析工具，不追求完整 SOC 功能。开发优先级从“先做全套工作台”调整为“先打通日志到威胁判断的闭环”。

### 第一版 UI 范围
1. **日志查询页（P0）**：选择数据源、时间范围和常用过滤条件；展示分页结果。
2. **日志详情（P0）**：查看标准化字段、必要的原始字段和来源引用。
3. **AI 分析面板（P0）**：对选中记录或受控查询结果发起分析、继续追问。
4. **分析结果（P0）**：威胁结论、类型、严重性、置信度、证据、反证、未知项和建议。
5. **简易总览（P1）**：数据源状态、分析数量和威胁发现概况。

暂缓复杂 Dashboard、完整告警工单/案例管理、报表、策略审批工作流和高级用户自定义功能。基础认证、后端权限、查询限制、脱敏和审计仍属于必要底座。

### 核心分析链路
日志查询/时间窗口 → 统计聚合与规则预筛选 → AI 对行为簇或告警组进行研判 → 按需查询代表性原始日志 → 输出带证据的威胁结论 → 用户复核。

AI 不应把所有原始日志无差别发送给模型。应优先分析聚合摘要和结构化事件，必要时再下钻少量日志。所有结论必须区分事实、推断和未知，并提供可定位证据。攻击尝试、WAF 拦截、请求到达后端和攻击成功必须分别判断。

### MVP Exit Criteria
- 至少一个已验证 WAF 数据源可完成查询、分页和详情查看。
- 可对选定日志/受控查询结果运行 AI 威胁分析。
- 对代表性攻击样本输出可追溯判断，并允许 Inconclusive。
- 分析结果可跳转至对应日志证据。
- 查询范围、样本量、截断状态、耗时和成本可见。
- AI 只读，不执行封禁或 WAF 策略修改。

### 调整后的开发顺序
1. 数据源查询和字段语义验证。
2. 最小日志查询 API 与 UI。
3. 统一事件/聚合摘要和证据引用。
4. AI 威胁分析工作流与评估集。
5. 右侧 AI 面板和简易独立会话页。
6. 根据实际使用反馈再扩展告警、事件管理和 Dashboard。
